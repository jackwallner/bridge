B1

After a time zone change with the app still in memory, the daily and game night reminders are rescheduled at the wrong time (9:00 AM becomes 6:03 AM)

mediumconfirmednotifications
Impact

A traveller gets the reminder at a wrong, odd time until the app is killed and relaunched (init rebuilds the Date from the saved 9 and 0). Touching the picker while it shows the shifted value saves the wrong time permanently.

How it happens
  1. In New York set the daily reminder to 9:00 AM (the Date is built from hour and minute in the New York zone).
  2. Leave the app suspended in the background and fly to Los Angeles (the process survives).
  3. Open the app. scenePhase active calls reconcileReminders, which calls scheduleReminder.
  4. scheduleReminder reads hour and minute from the stored Date with Calendar.current, now Los Angeles, and gets 6:03.
  5. The repeating reminder is rescheduled for 06:03 local. Settings also shows 6:03 in the picker. Game Night time shifts the same way.
Where
Shared/Services/AppSettings.swift:140Shared/Services/AppSettings.swift:235Shared/Services/AppSettings.swift:271Bridge/BridgeApp.swift:33
Suggested fix

Keep the saved hour and minute integers as the source of truth: have scheduleReminder and scheduleGameNightReminder use them directly, and rebuild reminderTime from them when the zone changes (NSSystemTimeZoneDidChange) or on foreground.

Evidence
reminderTime = Calendar.current.date(from: DateComponents(hour: hour, minute: minute)) ?? Date()
...
var parts = Calendar.current.dateComponents([.hour, .minute], from: reminderTime)
parts.second = 0
let trigger = UNCalendarNotificationTrigger(dateMatching: parts, repeats: true)

The wall time is stored as a Date with no year (year 1, local mean time offsets, hence the odd :03). That Date is only valid in the zone it was built in. The foreground reconcile added by the 2026-11-06 fixes re-reads it on every return to the app.

Checked by: Test testP3_Store_ReminderHourAfterZoneChange failed as predicted on a GitHub Mac (gh-sim run repo-imac853b-1120-113508-28488): a 9:00 setting made in New York reads as 6:03 after the zone moves to Los Angeles.

Not proven: The real flight and suspended-app case was not run. The test moved the process zone with NSTimeZone.default and the zone-change notification and read the same Calendar.current computation scheduleReminder uses. The picker display part is inferred, not run.

B3

Bridge Minute builds its day from the phone's calendar, so a Thai, Japanese-era, Hebrew or Islamic calendar phone gets different 'shared' questions

lowconfirmededge
Impact

The headline promise of the paid Bridge Minute ('the same five original questions for every member') is false for anyone whose system calendar is not Gregorian. Shared scores mean nothing and a calendar change orphans saved results. Only affects non-Gregorian calendar users, which includes the default for Thai region phones.

How it happens
  1. On an iPhone with region Thailand (default calendar Buddhist; Thai is one of the 16 shipped languages), open Bridge+ > Bridge Minute.
  2. The day key is built from Calendar.current, so today (2026-11-20) becomes '2569-11-20' instead of '2026-11-20'.

B4

lowconfirmededge
Impact

The 90-second best score is not comparable between runs, and a player can pause the clock at will. A call or notification mid-run does not cost the player time, so the stored best can be inflated.

B5

In zones where the clocks change at midnight (Chile, Cuba, Egypt, Lebanon, Azores), the day after the change counts as the same day: the streak loses a day and Get Started shows done

lowconfirmeddata
Impact

Players in zones whose daylight saving change happens at midnight lose one streak day and one daily mix once a year. Streak loss is the most visible retention number in the app.

How it happens
  1. Device time zone America/Santiago. Finish a drill on Sunday 2026-09-06 (clocks jump 00:00 to 01:00 that day, so local midnight does not exist).
  2. Finish a drill on Monday 2026-09-07.
  3. Streak stays 1 instead of 2, and lastActiveDay is moved to the 7th, so the lost day is not recovered.
  4. Alternatively finish the daily Get Started mix on the 6th: on the 7th Home still says today's session is done and a fresh mix lands tomorrow.
Where
Shared/Services/ProgressStore.swift:113Shared/Services/ProgressStore.swift:124Shared/Services/ProgressStore.swift:157
Suggested fix

Compare day keys instead of instants: count days between the two keys with the gregorian calendar at noon, or build the stored date with hour: 12 and compare startOfDay on both sides.

Evidence
return calendar.date(from: DateComponents(year: parts[0], month: parts[1], day: parts[2]))
...
return calendar.dateComponents([.day], from: day, to: calendar.startOfDay(for: now)).day ?? 0

The stored day key is turned back into 00:00 of that day. When 00:00 does not exist the date resolves to 01:00. The next day's startOfDay is 00:00, which is 23 hours later, and the .day difference of a 23 hour span is 0. dayGap returns 0 (same day) instead of 1.
